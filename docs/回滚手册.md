# 回滚手册

回滚的目标是恢复“上一个已验证版本”，不是在生产环境临时改代码。

## 触发条件

- 问卷无法提交或错误率明显上升。
- 新版本写入错误数据。
- 页面核心流程阻断。
- 出现安全或隐私风险。

## 前端回滚

1. 在 GitHub 找到最近一次验收通过的提交 SHA。
2. 从该提交创建修复分支，不使用 `git reset --hard` 改写公共历史。
3. 使用 `git revert <问题提交SHA>` 生成反向提交。
4. 通过 Pull Request 检查和人工确认后合并到 `main`。
5. 等待 Pages 工作流完成，再按验收清单执行冒烟测试。

检查点：线上页面的静态资源版本已变化，三题提交及成功页均正常。

## 云函数回滚

1. 在 GitHub 找到最近一次后端验收通过的提交 SHA。
2. 对问题提交执行 `git revert`，通过 Pull Request 合并。
3. `Deploy CloudBase function` 会把回滚后的代码更新到同一个 `survey` 函数。
4. 运行健康检查、正常提交、重复提交三个冒烟用例。
5. 检查 CloudBase 日志和数据库，确认错误率恢复。

如果自动发布不可用，可在已检出的稳定提交上执行：

```bash
npx --yes --package @cloudbase/cli@3.8.11 tcb login
npx --yes --package @cloudbase/cli@3.8.11 tcb fn code update survey -e <环境ID> --yes
```

## 数据回滚

代码回滚不会自动删除已经写入的数据。先暂停入口，再导出受影响记录，由开发确认筛选条件后修复或删除。不要直接清空或删除整张表。

## 回滚记录

每次回滚记录：故障时间、影响范围、问题提交、回滚提交、执行人、恢复时间、数据处理结果和后续改进项。
