# 问卷项目完整开发与部署流程

这是一套教学型但不省步骤的流程。目标不是最快把页面放上网，而是理解一个小功能如何从设计进入开发、测试、发布、监控和回滚。

## 1. 先理解全链路

```text
Figma / 旧 H5 验收基准
        ↓
Vue 组件与本地 mock
        ↓
Pull Request 自动测试与构建
        ↓
main 分支
   ├─ GitHub Pages：发布 H5
   └─ CloudBase：更新 survey 云函数
                          ↓
                    PostgreSQL 数据表
```

| 环节 | 主要负责人 | 产物 |
| --- | --- | --- |
| 需求和 UI 验收基线 | 设计 + 产品 | Figma 节点、文字、状态说明 |
| Vue 页面和交互 | 前端 | 组件、样式、单元测试 |
| 接口与数据校验 | 后端/全栈 | 云函数、数据契约、错误处理 |
| 云资源和密钥 | 云平台管理员 | CloudBase 环境、API Key、数据库 |
| 发布与回滚 | 开发 + 审批人 | Actions 记录、验收记录、回滚记录 |

## 2. 环境分层

专业项目至少区分本地、测试、生产。这个教学项目先完整跑通本地和一个 CloudBase 演示环境，再复制配置建立生产环境。

| 环境 | 用途 | 数据 | 是否公开 |
| --- | --- | --- | --- |
| Local | 日常开发 | 默认 mock | 否 |
| Demo/Test | 联调和学习部署 | 演示数据 | 可限时公开 |
| Production | 真实用户 | 正式数据 | 需要鉴权和审批 |

不要让测试和生产共用数据库表、API Key 或环境 ID。

## 3. 一次性准备ti

### 3.1 本机工具

目的：确保每位开发使用可复现的工具链。

1. 安装 Git、Node.js 22 和 npm。
2. 克隆仓库后进入 `survey-h5`。
3. 执行：

```bash
npm ci
npm ci --prefix cloudfunctions/survey
npm run test
npm run build
```

检查点：测试全通过且生成 `dist`。`npm ci` 使用锁文件，不会自行改依赖版本。

### 3.2 创建 CloudBase PostgreSQL 演示环境

目的：提供云函数运行环境和持久化数据库。

1. 在腾讯云 CloudBase 控制台创建环境，例如 `survey-demo`。
2. 记录环境 ID；名称和环境 ID 不是一回事。
3. 打开 PostgreSQL 的 SQL 编辑器。
4. 执行 [`database/migrations/001_create_survey_submissions.sql`](../database/migrations/001_create_survey_submissions.sql)。
5. 确认生成 `public.survey_submissions` 表，且没有向普通角色添加访问策略。
6. 不向网页暴露服务端 API Key 或数据库密钥。

输出：一个演示环境 ID 和一张空的 `survey_submissions` 表。

### 3.3 首次部署事件函数

现有代码使用 `index.main(event)`，属于事件函数，由 HTTP 访问服务把请求转换成 event。它不是监听 9000 端口的 HTTP Web 函数。

```bash
npx --yes --package @cloudbase/cli@3.8.11 tcb login
export CLOUDBASE_ENV_ID=你的环境ID
npx --yes --package @cloudbase/cli@3.8.11 tcb fn deploy survey -e "$CLOUDBASE_ENV_ID"
```

首次部署读取根目录 `cloudbaserc.json`，运行时固定为 Node.js 20.19。函数依赖由 `npm ci --prefix cloudfunctions/survey` 安装后随代码包上传，CI 不依赖云端临时解析依赖版本。

检查点：CloudBase 控制台出现名为 `survey` 的事件函数，入口是 `index.main`。

### 3.4 配置函数环境变量

在控制台为演示函数设置：

| 名称 | 演示值 | 说明 |
| --- | --- | --- |
| `ALLOWED_ORIGIN` | `https://gaotiantiantian.github.io` | CORS 只允许 Pages 来源 |
| `DEMO_SERVICE_NAME` | `投顾服务` | 成功页演示文案 |
| `DEMO_SERVICE_END_DATE` | `2026-11-29` | 演示到期日 |

检查点：不要把任何 Secret 写入 `cloudbaserc.json`。以后使用完整部署命令前，先确认 CLI 不会覆盖控制台环境变量；日常 CI 只执行 `fn code update`。

### 3.5 创建 HTTP 访问路由

在 CloudBase HTTP 访问服务中创建 `/survey` 路径并关联 `survey` 事件函数，开启演示所需的公网访问，复制完整 HTTPS URL。

检查点：浏览器 GET 该 URL 返回：

```json
{"status":"ok","database":"connected"}
```

### 3.6 配置 GitHub

在仓库 Settings 中完成：

1. 将公开的完整函数 URL 保存到 `.env.production` 的 `VITE_CLOUDBASE_FUNCTION_URL`。
2. 创建 GitHub Environment：`production`，设置审批人。
3. 在 `production` Environment Secrets 中添加：
   - `CLOUDBASE_ENV_ID`
   - `CLOUDBASE_API_KEY`
4. API Key 优先使用绑定单个 CloudBase 环境的环境级密钥，不使用可操作整个腾讯云账号的永久 SecretKey。

检查点：Secret 页面保存后不能再次查看明文；密钥不出现在代码、截图和聊天记录中。

## 4. 每个需求的日常开发

1. 从最新 `main` 创建分支，例如 `feature/survey-copy`。
2. 设计先明确 Figma 节点、文字、交互状态和验收视口。
3. 开发阅读相关组件，说明最小修改方案后编码。
4. 本地默认使用 mock，避免开发时污染云数据库。
5. 完成后运行测试和构建。
6. 提交分支并创建 Pull Request。
7. CI 通过后，由设计做视觉验收、开发做功能验收。
8. 审批后合并到 `main`。

输入：明确需求和设计基准。输出：可审查的 PR，而不是直接覆盖线上文件。

## 5. 自动化流水线分别做什么

### `Verify pull request`

PR 创建或更新时执行干净安装、测试、构建和云函数语法检查。失败时不允许合并。

### `Deploy web to GitHub Pages`

合并到 `main` 后，测试并构建 Vue，从 `.env.production` 读取云函数公开地址，再发布 `dist`。

### `Deploy CloudBase function`

只有 `cloudfunctions/survey/**` 变化时触发。通过 `production` Environment 审批后登录 CloudBase，只更新函数代码，不改环境变量和 HTTP 路由。

## 6. 发布后的验收

发布完成不等于验收完成。按 [`验收清单.md`](./验收清单.md) 检查：

1. GET 健康检查。
2. 完成一次真实问卷提交。
3. CloudBase PostgreSQL 表中找到相同 `request_id`。
4. 重复请求不产生第二条记录。
5. 查看函数错误率和日志。
6. 三个移动端视口完成 UI 冒烟检查。

## 7. 监控和维护

- 每次发布后查看 CloudBase 调用次数、平均耗时、错误率和内存。
- 日志只记录 `requestId` 和错误类型，不记录完整答卷、密钥或个人敏感信息。
- 演示数据建议保留不超过 30 天，并记录清理时间。
- 每月确认 API Key 是否仍需要，人员变更时立即轮换。
- 依赖升级单独开 PR，不与 UI 改动混在一起。
- 当前 SDK 间接依赖风险与缓解措施见 [`安全风险记录.md`](./安全风险记录.md)。

## 8. 回滚

出现阻断故障时，先停止继续发布，按 [`回滚手册.md`](./回滚手册.md) 回到上一个已验收提交。代码回滚和数据修复是两件事，不能通过删库代替代码回滚。

## 9. 当前项目还不是正式生产系统

目前可以专业地跑通“设计—开发—测试—部署—存储—验收—回滚”的学习流程，但公开演示接口没有真实用户鉴权、限流、防刷和正式权益审计。它适合教学和测试，不适合直接收集真实客户信息。
